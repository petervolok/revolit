# Конструктор шаблонов конфигураций — ход работ

Решение и обоснование: [08-decisions.md, Р-42](08-decisions.md#р-42-конструктор-шаблонов-конфигураций-кубики--код-уровень-сборки-сборка-шаблона-из-них--данные-без-пересборки).

**Как продолжить с любого места:** открыть этот файл → найти первый этап не в статусе «готов» →
прочитать его раздел ниже → работать. Каждый этап — отдельный коммит (`Конструктор, этап N: …`).

## Этапы

| # | Этап | Статус | Коммит |
|---|---|---|---|
| 0 | Разбор готовых продуктов, поиск границ универсальных макро-кубиков | не начат | |
| 1 | Формат манифеста кубика (схема пропсов, слоты, категории, правила вложенности) | не начат | |
| 2 | Первый набор кубиков (по итогам этапа 0) + рендер-интерпретатор дерева | не начат | |
| 3 | Хранение дерева конфигурации (данные, без пересборки) + каталог/витрина | не начат | |
| 4 | Первая настоящая конфигурация, собранная вручную, для одного реального клиентского продукта | не начат | |
| 5 | ИИ-сборщик: собирает дерево кубиков по задаче оператора, валидация по манифестам | не начат | |

Статусы: не начат · в работе · готов · заблокирован (с причиной).

## 0. Разбор готовых продуктов — ведётся вне этого репозитория

**Решение владельца (23 сентября 2026):** сам разбор (изучение продуктов, поиск границ кубиков,
итерации по универсальности) — открытый, потенциально многоитерационный творческий процесс без
чёткого критерия "готово". Ведение его в рабочей сессии с кодом раздувало бы историю и отвлекало
контекст от остальной разработки. Решено вести его в отдельной сессии/переписке, не привязанной
к этому репозиторию, и приносить сюда только готовый результат.

Полное задание для той сессии (контекст платформы, что уже есть в ядре, цель исследования,
формат каталога кубиков и формат тестового проекта) — отдельным файлом, переданным владельцу
напрямую (не хранится в репозитории, так как это входной материал для процесса, а не решение).

**Что приносится обратно, когда этап 0 завершён:**
1. Каталог кубиков — универсальный набор, проверенный минимум на 4-5 структурно разных реальных
   продуктах.
2. Один полностью собранный тестовый проект (конкретный клиентский продукт), целиком выраженный
   как дерево кубиков из каталога — без исключений/особых случаев за пределами каталога.

## Как продолжить, когда результат принесён

1. Завести в этом репозитории тестовую папку/ветку (не трогая боевой код), собрать из принесённого
   дерева кубиков реальные React-компоненты первого черновика — по формату манифеста, который
   принесли, но уже в виде кода.
2. Развернуть тестовую сборку на отдельном порту на ВПС, рядом с боевыми сервисами, не заменяя их.
3. Смотреть вживую, что получилось, и по итогам править либо конкретные кубики, либо сам формат
   манифеста — итеративно, каждая правка отдельным коммитом с отчётом, как принято в этом проекте.
4. Только после того как этот цикл даст рабочий, устраивающий владельца результат — переходить
   к этапам 1-5 из таблицы выше (формальный манифест, каталог/витрина, ИИ-сборщик).
