## 0. Зачем разбор готовых продуктов идёт первым этапом

Ошибка, которой нужно избежать: спроектировать кубики "от головы", под один воображаемый продукт,
и получить набор, который на втором реальном продукте придётся кроить заново. Р-42 прямо требует
обратного порядка — сначала посмотреть на несколько разных по смыслу реальных продуктов
(CRM/каталог/бронирование/заявки — что выберем для разбора) и найти, на каком уровне резать, чтобы
один и тот же кубик встречался в разных продуктах не притянутым за уши, а естественно.

**Как будет оформлен результат.** Список изученных продуктов (что смотрели, что отметили), и
таблица кандидатов в кубики: название, что это в интерфейсе (макро-уровень — например «карточка
записи со списком полей», «доска с колонками», «форма фильтра», а не «кнопка» — единицы разбора
должны быть достаточно крупными, чтобы 30-100 из них собирали целый продукт, а не тысячи мелких
атомов). Для каждого кандидата — в каких из разобранных продуктов он встретился и чем отличалось
использование (это и есть проверка на универсальность до того, как будет написан код).

## Как продолжить прямо сейчас

Этап 0 не начат. Первое действие — договориться с владельцем, какие 3-5 реальных продукта
разбирать (свои готовые примеры из `EntityTemplatePreset`/roadmap — «Контрагенты», «Заказы»,
«Банкеты» — это данные внутри одного продукта-конструктора, для разбора нужны именно **разные
по устройству клиентские продукты**, не наборы полей одной CRM).
