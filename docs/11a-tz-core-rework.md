# ТЗ: переработка ядра Revolit под двухсерверную архитектуру проекта «Времена года»

Дата: 19.09.2026. Статус: черновик для дальнейшего согласования, не прототип — полная переработка.
Опирается на факты, проверенные в коде `revolit` на дату документа, и на согласованные решения
из «ТЗ: архитектура «основной + страховочный сервер»» и «ТЗ модернизации CRM «Времена года»
(редакция 4)».

## 0. Рамки документа

Документ описывает изменения в **ядре** платформы Revolit (`core/`), не в прикладном плагине
банкетной CRM. Плагин (сущности «Заказ», «Клиент», процесс банкета, отчёты, календарь залов)
описывается отдельным ТЗ и здесь не затрагивается, кроме мест, где ядро должно предоставить
плагину новую возможность (события, признак чувствительности).

## 1. Цель

Перевести доступ к данным в ядре Revolit с прямых вызовов Prisma внутри процесса Next.js на
доступ через шину сообщений (RabbitMQ) и агента, чтобы реализовать схему из «ТЗ: архитектура
«основной + страховочный сервер»»: сервер №1 не хранит и не видит ничего о существовании
сервера №2, а сервер №2 подключается к шине сервера №1 как обычный клиент с более высоким
приоритетом потребителя. Одновременно закрываются два пробела платформы, необходимые для
раздела 3 «Основа для этапа 2» ТЗ модернизации CRM: доменные события и фоновые задачи.

## 2. Что остаётся неизменным

- Принципы платформы 1, 3–7 из `docs/10-plugin-authoring.md` не меняются.
- Принцип 2 меняется частично: доступ к БД перестаёт быть прямым Prisma-вызовом в процессе,
  становится вызовом через порт данных (раздел 3). Само правило «плагин — код, вкомпилированный
  в сборку, без динамической загрузки» не затрагивается.
- Контракт плагина (`ModuleManifest`, чек-лист добавления плагина) не меняется — существующие
  и будущие плагины продолжают писаться так же, разница скрыта внутри сервисов ядра.
- Модель сущностей/процессов/задач (`EntityRecord.data` как JSON и т. д.) не меняется, кроме
  одного нового поля (раздел 4.2).

## 3. Архитектура доступа к данным

### 3.1. Порт данных (DataPort)

Вводится интерфейс `DataPort` (`core/data/port.ts`), параметризующий операцию как
`{ model, operation, args }` — по образцу уже существующих сменных портов (`MailPort`,
`StoragePort`). Две реализации:

- `LocalDataPort` — прямой вызов Prisma-клиента (текущее поведение, режим `direct`).
- `BusDataPort` — публикует операцию в RabbitMQ и ждёт ответа по `correlationId` (RPC-паттерн
  с очередью ответа `reply-to`), режим `bus`.

Режим переключается переменной окружения процесса (`DATA_MODE=direct|bus`), не значением в БД —
секрет и адрес шины не могут храниться в базе, которую они же обслуживают.

### 3.2. Встраивание без переписывания сервисов

Порт встраивается через расширение Prisma-клиента (`prisma.$extends`) на уровне `core/data/prisma.ts`:
расширение перехватывает операции моделей, подлежащих проксированию, и перенаправляет их в
`BusDataPort` вместо реального похода в базу. Сервисы (`core/entities/service.ts`,
`core/processes/service.ts`, `core/tasks/service.ts`, `core/attachments/service.ts`) продолжают
писать `prisma.entityRecord.findMany(...)` как сейчас — перехват происходит ниже, без правки
сигнатур. Требуется решить сериализацию нестандартных типов аргументов (Date, BigInt) для
передачи по шине (JSON с ISO-датами и функцией-ревивером на обеих сторонах).

### 3.3. Что проксируется, что нет

Проксируются доменные модели: `EntityTemplate`, `EntityField`, `EntityRecord`,
`EntityTemplatePreset`, `ProcessTemplate`, `ProcessStage`, `ProcessInstance`,
`ProcessHistoryEntry`, `Task`, `Attachment`.

**Не проксируются** (прямой Prisma, минуя шину и агента): `User`, `Role`, `UserRole`, `Session`,
`LoginCode`, `PasswordResetToken`, `AuditLog`, `Program`, `ProgramSettings`, `ModuleToggle`,
`AiKeyGroup`, `AiKey`. Приложение выполняется только на сервере №1 и для этих моделей всегда
обращается к своей же локальной БД №1 напрямую — переключение агентов их не касается, потому что
через шину (и значит через агента №2) эти операции никогда не проходят.

**Важное следствие: эти данные физически существуют только в БД №1.** В БД №2 те же таблицы
присутствуют (общая схема, миграции применяются к обеим базам), но остаются пустыми — агент №2
их не заполняет, писать туда некому. Это не наносит вреда переключению между агентами (раздел 5),
потому что точка входа пользователей не переключается — переключается только то, какой агент
обслуживает доменные операции.

Открытый риск (см. 11.6): если доменная запись хранит ссылку на пользователя (например,
`assigneeId` менеджера в `data`), а отдельный интерфейс на сервере №2 обращается к БД №2 напрямую
и должен показать имя — взять его будет не из чего, таблица `User` там пустая. Решение
(урезанная одностороняя копия «id → имя» без пароля и сессий, либо резолвинг имени через API
сервера №1) не выбрано.

### 3.4. Массивные транзакции

4 места в коде используют `prisma.$transaction([...])`: `core/api/users/[id]/route.ts`,
`core/processes/service.ts` (`reorderFields`-аналог для этапов), `core/entities/service.ts`
(`reorderFields`), `core/api/auth/password-reset/confirm/route.ts`. Первое и последнее — на
непроксируемых моделях (auth), не меняются. Два оставшихся — на доменных моделях, заменяются на
`dataPort.runBatch([...])`, которая на стороне агента оборачивается в настоящий
`prisma.$transaction`, чтобы пакет выполнился атомарно одним сообщением шины.

### 3.5. Агент

Новый процесс `apps/agent` (общий образ для роли №1 и №2, различие только в переменных
окружения — строка подключения к своей БД и приоритет потребителя). Слушает очередь операций,
выполняет их настоящим Prisma-клиентом своей базы, отвечает в очередь `reply-to` с тем же
`correlationId`. Подтверждение сообщения (`ack`) — только после успешной записи; при обрыве
агента посреди обработки сообщение возвращается в очередь (redelivery).

### 3.6. Идемпотентность при повторной доставке

Redelivery способна выполнить одну операцию `create` дважды. Решение: идентификатор новой
записи (`cuid()`) генерируется в сервисе ядра **до** вызова порта, а не автогенерацией Prisma
на стороне агента (`@default(cuid())` меняется на явную передачу `id` в `create`). Повторная
доставка с тем же `id` превращается в `upsert`, не создаёт дубликат. Требует точечной правки
всех `create`-вызовов на проксируемых моделях.

### 3.7. Приоритет потребителя и автоматический возврат

Агент запускается с параметром приоритета (`AGENT_PRIORITY`: 0 для роли №1, выше — для роли №2),
передаваемым в `basic.consume` как `x-priority` (см. «ТЗ: архитектура…», разделы 3–4, 7). Пока
подключён потребитель с более высоким приоритетом — все сообщения идут ему; при разрыве RabbitMQ
автоматически возвращает поток потребителю с меньшим приоритетом. Ядро Revolit не содержит кода,
знающего, что где-то есть второй агент — оно всегда работает с одним и тем же локальным адресом
шины.

## 4. Признак чувствительности и его распространение

### 4.1. Правило — конфигурация, не код

Новая модель `SensitivityRule` (`core/prisma/core.prisma`): `programId`, набор условий в JSON
(поле, оператор, значение), редактируется директором через API/интерфейс без участия
разработчика (согласовано ранее). Хранится как обычные данные программы — по тому же принципу,
что и остальные настраиваемые сущности платформы.

### 4.2. Новое поле у записи

`EntityRecord.data` — непрозрачный JSON без индекса, фильтровать по нему в репликации нельзя.
Добавляется служебное поле `EntityRecord.sensitive Boolean @default(false)`, вычисляемое
агентом при создании/изменении записи на основе `SensitivityRule` текущей программы.

### 4.3. Распространение признака

`ProcessInstance`, `Task`, `Attachment`, связанные с чувствительной `EntityRecord` через
`entityRecordId`, также помечаются `sensitive=true` — агент делает это каскадно при создании
записи или изменении связи. Требуется отдельно продумать случай смены значения (запись перестала
быть чувствительной) — снятие признака с уже созданных связанных объектов.

### 4.4. Временное правило на запуск

Согласовано ранее: на запуск используется жёсткое правило «способ оплаты = наличные» для
сущности «Заказ», без общей конфигурации порогов — она добавляется позже, в работающей системе,
без изменения кода (только запись в `SensitivityRule`).

## 5. Репликация и переключение серверов

### 5.1. Что лежит в какой базе

БД №1 хранит все непроксируемые (учётные) модели полностью и только те доменные записи, где
`sensitive=false`. БД №2 хранит все доменные записи без исключений; учётные таблицы в ней пусты
(раздел 3.3). Обеспечивается тем, что запись самой записи
всегда идёт через текущего приоритетного агента: агент №2 (пока подключён) пишет в БД №2 всегда
и параллельно дублирует в БД №1 только то, что не чувствительно.

### 5.2. Почему сервер №1 ничего не знает о сервере №2

В коде `core`/`apps/crm`/`apps/agent`, поставляемом на сервер №1, нет ни одного упоминания
адреса или учётных данных сервера №2: агент роли №1 конфигурируется только адресом своей же
локальной шины и своей БД. Агент роли №2 — тот же образ с другими переменными окружения,
запущенный физически на сервере №2, инициативно подключается к публичному адресу шины
сервера №1. Правило «никаких следов» (см. «ТЗ: архитектура…», раздел 1) выполняется на уровне
поставки: то, что развёртывается на сервере №1, не содержит второй конфигурации.

### 5.3. Состав каждого сервера

Сервер №1: приложение Next.js + локальная шина (RabbitMQ) + локальный агент (роль №1,
приоритет 0) + БД №1. Сервер №2: агент (роль №2, приоритет выше) + БД №2 + управляющий код
для Telegram/MAX (см. отдельное ТЗ). Приложение всегда обращается к локальной шине сервера №1,
независимо от того, кто сейчас её слушает.

## 6. Доменные события

- `CoreEventMap` расширяется событиями сущностей, процессов и задач (сейчас в коде реально
  эмитятся только `user.*`, `role.*`, `auth.*` — проверено по `core/events/coreEvents.ts` и
  местам вызова `coreEvents.emit`). Добавляются как минимум:
  `entity.record.created`, `entity.record.updated`, `entity.record.deleted`,
  `process.instance.moved`, `process.instance.statusChanged`, `task.created`, `task.completed`.
- Эмитировать события должен **агент**, после подтверждённой записи в БД, а не сервис ядра —
  иначе при dual-write событие могло бы уйти раньше, чем данные реально сохранились в обеих
  базах, либо продублироваться.
- Подписка (`register(ctx.events)` в манифесте модуля) не меняется — плагины подписываются так
  же, как описано в текущем контракте.

## 7. Фоновые задачи

Платформа сейчас не имеет ни фоновых задач, ни cron, ни очередей (см. `docs/10-plugin-authoring.md`,
раздел 13) — это разрыв с требованиями раздела 3 ТЗ модернизации CRM (напоминания «3 дня до
банкета», «просроченная оплата»). Поскольку с приходом агента и шины в системе всё равно
появляется отдельный процесс, туда же добавляется простой планировщик:

- Новая модель `ScheduledJob` (`programId`, `key`, `cronExpression`, `lastRunAt`, `enabled`).
- Раннер в составе `apps/agent` (или отдельный процесс `apps/scheduler`, если совмещение с
  агентом данных окажется неудобным на практике — решить на этапе реализации), проверяющий
  расписание и публикующий обычные доменные события, на которые реагируют плагины/бот.

## 8. Секреты и конфигурация

Адрес и учётные данные шины передаются процессу через переменные окружения при старте, не через
`ProgramSettings` — это осознанное исключение из принципа платформы «секреты живут в БД, не в
файлах окружения». Причина: секрет для доступа к шине не может храниться в базе, которую этот же
секрет открывает. Оформляется отдельной записью в `docs/08-decisions.md` с явным объяснением
исключения.

## 9. Миграции

Обе базы получают одинаковую схему (общий `schema.prisma`, как и сейчас). Каждый агент применяет
миграции своей базы при старте — по аналогии с текущим `docker-entrypoint.sh`, но раздельно на
каждом сервере, а не централизованно из приложения. Совместимость версии схемы между агентом №1
и агентом №2 при неодновременном обновлении серверов не проверяется автоматически — открытый
вопрос (раздел 11).

## 11. Открытые вопросы

1. Задержка каждого Prisma-вызова через шину против прямого вызова в процессе — нужно замерить
   на самых «тяжёлых» экранах (аналоги `_view`/`_edit` старой CRM с десятками последовательных
   запросов) и решить, нужно ли пакетирование нескольких операций одного экрана в одно сообщение.
2. Совместимость версий схемы между агентами при неодновременном обновлении серверов — нет
   автоматической проверки, нужно решить, вводить ли её или запретить неодновременные обновления
   регламентом.
3. `SensitivityRule` как модель ядра или как специфика плагина банкетной CRM — если это
   ядро, это первое расширение платформы, продиктованное конкретным клиентом, а не общей
   потребностью; стоит решить, действительно ли оно универсально для всех будущих проектов на
   Revolit, или его следует держать в плагине.
4. Снятие признака `sensitive` с уже созданных связанных объектов при изменении правила или
   данных записи — правило каскадного обновления не определено (раздел 4.3).
5. Совмещать ли планировщик фоновых задач с агентом данных в одном процессе или выносить
   отдельным сервисом — зависит от нагрузки, решить при реализации.
6. Ссылки доменных записей на пользователей (`assigneeId` и подобные) и отдельный интерфейс на
   сервере №2, читающий БД №2 напрямую: таблица `User` там пуста, имя по id взять неоткуда.
   Нужно выбрать: одностороння копия «id → имя» в БД №2 (без пароля и сессий) или резолвинг имени
   через API сервера №1 (см. раздел 3.3).
