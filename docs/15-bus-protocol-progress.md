## Отчёты по этапам

### Этап 1. Протокол и применитель

**Сделано.**
- `core/bus/protocol.ts`: константы потоков, ключи `event`/`changes`, типы `DataChange`,
  `BusChangesMessage`, `BusCompletion`.
- `core/bus/applier.ts`: `applyChanges` — атомарное применение изменений одной операции, состояние
  вместо дельты, защита по `updatedAt`, составной ключ у `UserRole`, `Prisma.DbNull` для null в Json.
- `apps/agent`: обменники и очередь применения объявляются при старте; отдельный канал с prefetch 1
  применяет изменения по порядку и публикует COMPLETION; за каждую запись через MAIN тоже
  публикуется COMPLETION (универсально, осмысленно и без второго агента).
- `core/bus/busPort.ts`: приложение слушает EVENTS по ключу `event`.
- `tools/protocol-smoke.ts` и шаг CI: внешний издатель шлёт изменения так же, как будет агент №2.
  Проверяется применение, повтор, устаревший и более новый снимок, удаление, цепочка с внешними
  ключами, составной ключ, Json-null, ошибка применения и продолжение работы после неё,
  подтверждение за запись через MAIN.

**Не сделано / честно.** Агент №2 пока работает по старой схеме (прямое дублирование), в его коде
исправлено только объявление обменника. Проверка идёт на одной базе.

### Этап 2. Агент №2 на новой схеме

**Сделано.**
- `apps/agent2/src/index.ts` переписан. Запись: журнал операций проверяется по `operationId`; если операция
  уже выполнена, она не исполняется снова (берутся сохранённые ответ и изменения). Иначе — одна
  транзакция в БД №2: исполнение, сбор изменений, запись в журнал. Затем изменения уходят в EVENTS,
  агент ждёт COMPLETION (по умолчанию 20 с, `AGENT_COMPLETION_TIMEOUT_MS`) и только после этого
  отвечает приложению (решение владельца: отвечать после) и подтверждает команду в MAIN. Нет
  подтверждения или `ok=false` — команда возвращается в MAIN через 5 с. Чтение идёт по короткому пути
  без журнала и подтверждений.
- `apps/agent2/src/changes.ts` (заменил `dualWrite.ts`): тронутые ключи → итоговое состояние строк →
  фильтр чувствительности **по каждой строке отдельно** (раньше решение принималось по операции;
  `updateMany` по чувствительным записям раньше не фильтровался вовсе). Удаление чувствительной строки
  в БД №1 не сообщается.
- Новая модель `OperationLog` и миграция только в схеме agent2 (`operations.prisma`); очистка записей
  старше недели.
- Прямое подключение к БД №1 удалено целиком: `DATABASE_URL_PRIMARY` и `createPrimaryClient` убраны
  из кода и из `docker-compose.agent2.yml`.
- `core/data/localPort.ts`: `callOperation` экспортирована — агент исполняет пакет внутри своей транзакции.
- `tools/agent2-smoke.ts` переписан под новый модуль: 19 проверок через настоящие транзакции БД №2
  (создание, изменение, удаление, `*Many`, связанные задачи, структура, пакет с составным ключом, журнал).

**Известные ограничения.**
- Если применитель на сервере 1 не работает вообще, записи через агента №2 зависают: команда не
  подтверждена, приложение отвечает таймаутом. Это следствие инварианта; заметит мониторинг очереди
  (рост глубины, оповещение в Telegram).
- Запись, ставшая чувствительной после изменения, остаётся в БД №1 в прежнем виде (как и в Р-41);
  скрывать её удалением не решено.
- Постоянная ошибка применения на сервере 1 даёт цикл «вернуть команду — снова не применилось» каждые
  ~5 с до вмешательства; снимет только исправление причины.

**Проверено:** типы и сборка в CI. Сквозная работа агента №2 с настоящей шиной и двумя базами — этап 3.
