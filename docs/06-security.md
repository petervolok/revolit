# Безопасность

Защита заложена с самого начала, а не добавлена потом. Ниже — что реализовано
и проверено на практике.

## Пароли

| Мера | Как сделано |
|---|---|
| Хранение | bcrypt, стоимость 12. Открытых паролей в базе нет |
| Политика | не короче 10 символов, обязательны буквы и цифры |
| Задание пароля новым сотрудником | администратор пароль не знает — сотрудник задаёт сам по ссылке из письма |
| Смена пароля | требует подтверждения текущего |
| Последствие смены | все активные сессии завершаются |

## Двухфакторная аутентификация

Второй фактор — код на почту. Включён всегда, не отключается.

- шестизначный код, действует 10 минут;
- не более 5 попыток ввода, после чего код сгорает;
- код одноразовый — повторный ввод отклоняется;
- при новой попытке входа прошлые коды гасятся;
- в базе хранится только хеш кода.

## Защита от подбора

- 5 неудачных попыток пароля — блокировка на 15 минут;
- заблокированного не пускает даже верный пароль;
- снять блокировку может администратор;
- ответ на неверный пароль и на несуществующую почту **одинаковый** — нельзя выяснить,
  заведена ли такая учётная запись;
- при неизвестной почте выполняется холостая проверка пароля, чтобы время ответа
  не выдавало результат.

## Сессии

- случайный токен 32 байта, в базе только его хеш;
- cookie недоступна скриптам страницы (httpOnly), с ограничением на межсайтовые
  переходы (sameSite), по защищённому соединению в рабочем режиме;
- срок жизни 7 дней;
- отметка активности не чаще раза в 5 минут, чтобы не нагружать базу;
- пользователь видит свои активные сессии и может завершить остальные;
- отключение сотрудника мгновенно обрывает все его сессии.

## Восстановление пароля

- ссылка одноразовая, действует 1 час;
- в базе только хеш ссылки;
- ответ одинаковый для любой почты — существование учётной записи не раскрывается;
- после смены пароля все сессии завершаются.

## Приглашение сотрудника

- ссылка действует 48 часов, отправляется повторно по требованию;
- прошлые ссылки при этом гасятся;
- отключённому сотруднику приглашение не отправляется.

## Разграничение доступа

Проверка на трёх уровнях, каждый самостоятельный:

1. **Обработчики запросов** — без права отдают отказ. Это главный рубеж.
2. **Страницы** — без права перебрасывают на главную.
3. **Меню** — недоступные пункты не показываются.

Скрытие пункта меню защитой не считается — данные закрыты на уровне запросов.

## Защита от потери управления

- нельзя снять с себя роль администратора, если других администраторов нет;
- нельзя отключить последнего администратора;
- права системной роли администратора неизменяемы;
- системную роль нельзя удалить;
- роль, назначенную сотрудникам, нельзя удалить, пока её не снимут.

## Журнал действий

Фиксируется: вход, неудачный вход, блокировка, отправка и ошибка кода, выход,
запрос и завершение смены пароля, создание, изменение и отключение сотрудника,
операции с ролями.

Для каждой записи: кто, что, когда, с какого адреса, с какого устройства.
Сбой записи в журнал не срывает основную операцию.

## Что проверено на практике

| Проверка | Результат |
|---|---|
| Неверный пароль и несуществующая почта | одинаковый ответ |
| 5 неудачных попыток | блокировка, верный пароль тоже не пускает |
| Повторный ввод использованного кода | отклонён |
| Доступ к разделам без входа | переброс на страницу входа |
| Роль без прав: запрос данных | отказ |
| Роль без прав: прямой заход на страницу | переброс на главную |
| Снятие с себя роли администратора | запрещено |
| Отключение сотрудника | сессии оборваны, вход невозможен |
| Повторное использование ссылки восстановления | отклонено |
| Слабый пароль | отклонён |

## Безопасность опубликованных сайтов

Касается CMS (шаг 13 [дорожной карты](07-roadmap.md)). Отдельная тема от
безопасности самой платформы, описанной выше: здесь речь о том, что происходит
на хостинге клиента, куда наш контроль не дотягивается напрямую.

**Мы не храним доступы к хостингу клиентов.** Публикация устроена в обратную
сторону: клиентский сайт сам обращается к нам через небольшой агент, а не мы
подключаемся к чужому хостингу с паролем. Значит, утечка нашей базы не даёт
доступа ни к одному сайту клиента. Подробности и разбор — [Р-15](08-decisions.md).

**Пакеты обновления подписываются.** Ключ подписи не лежит ни в базе, ни на
боевом сервере. Агент отказывается ставить неподписанный пакет. Без этого
предыдущий пункт не работает: получивший доступ к раздаче мог бы подсунуть
свой пакет. — [Р-16](08-decisions.md).

**Ни один единичный взлом не даёт полного доступа.**

| Что скомпрометировано | Что теряют сайты клиентов |
|---|---|
| Наша база целиком | ничего — пакет без ключа не подделать |
| Наш боевой сервер целиком | ничего, если ключ подписи хранится отдельно |
| Хостинг одного клиента | только этот сайт, не остальные |

**Возможности агента на хостинге клиента ограничены нарочно:** скачать пакет,
проверить подпись, разложить файлы в свою папку. Не умеет ничего сверх этого —
чем меньше умеет, тем меньше вред при взломе самого хостинга клиента.

**Чего это не решает.** Если взломан сам хостинг клиента, агента на нём могут
подменить — это уже вне нашего контроля. Смягчается проверкой целостности
и оповещением при расхождении, но полностью не снимается.

## Запланировано

- **Корпоративный вход** (LDAP, SAML) — платный модуль, см. [модули](04-modules.md).
- **Ограничение частоты запросов** по адресу, а не только по учётной записи.
- **Просмотр журнала в интерфейсе** — сейчас доступен только в базе.
- **Отдельное подтверждение для опасных действий** (удаление данных, смена почты).
- **Проверка на утёкшие пароли** при задании нового.

## Особая осторожность

**Пароль почтового ящика.** Передан в переписке открытым текстом, поэтому подлежит смене.
В файлы проекта не записывается — папка проекта синхронизируется в облако.
Живёт только в переменных окружения на сервере.
См. [соглашения](09-conventions.md).
