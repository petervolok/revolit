# Архитектура

## Общая картина

```
revolit-platform/
├── ядро/            общий каркас — переиспользуется всеми продуктами
├── crm/             конструктор корпоративных систем
└── cms/             конструктор сайтов
```

Продукты разворачиваются как **независимые сервисы со своими базами**.
Общий у них только исходный код ядра.

## Главный принцип

> **У ядра есть опубликованный интерфейс и запечатанные внутренности.**

Модули пользуются только опубликованным интерфейсом и никогда не лезут во внутреннее
устройство ядра. Тогда ядро можно переписывать внутри сколько угодно — модули продолжат
работать.

Заимствовано у VS Code, где расширения работают через строго очерченный набор возможностей
и не имеют доступа к внутренностям редактора.

## Модульный монолит

Для нашего масштаба — **модульный монолит**, не микросервисы. Границы между модулями
строгие, но всё работает одним приложением. Разделение на отдельные сервисы — только
когда упрёмся в реальное ограничение.

Исключение: CRM и CMS — разные продукты, а не модули одного. Они разделены изначально.

## Два типа расширений

Различие принципиальное, путать нельзя.

### Модули сборки

Могут всё: свои таблицы, страницы, разделы, обработчики. Подключаются **при сборке**
программы — «закинул архив и заработало» не выйдет, нужна пересборка.

Так устроены: конструктор CRM, CMS, ИИ-сборка, корпоративный вход.
Пишутся нами и сторонними разработчиками.

### Расширения на данных

Живут в базе, применяются **мгновенно, без пересборки**: сущности, поля, роли, процессы,
настройки интерфейса.

**Это то, что делает конструктор.** Конечный пользователь расширяет систему только так —
пересборка ему не нужна никогда.

## Из чего складывается расширяемость ядра

### 1. Сменные части (порты)

Ядро объявляет, *что* делает, модуль — *как*:

| Часть | По умолчанию | Заменяется на |
|---|---|---|
| Вход | пароль + код на почту | корпоративный каталог (LDAP, SAML) |
| Хранение файлов | диск сервера | облачное хранилище |
| Почта | обычный SMTP-сервер | почтовый сервис по API |
| Задачи по расписанию | база | отдельная очередь |
| Поиск | база | поисковый движок |

Замена реализации не затрагивает остальное ядро.

**Правило:** внешние зависимости не должны быть обязательными. По умолчанию всё работает
на одном сервере с базой. Иначе установка у клиента превращается в мучение —
см. [развёртывание](05-deployment.md).

### 2. Реестр вкладов

Модуль объявляет в своём описании, что он добавляет:

- пункты меню
- страницы и адреса
- права доступа
- сущности и поля
- разделы настроек
- задания по расписанию
- подписки на события

Ядро читает описание и подключает. Никакой ручной проводки.

Заимствовано у VS Code (файл описания расширения) и Directus (разложенная классификация
типов расширений — не «один универсальный крючок», а понятные категории).

### 3. Шина событий

Ядро сообщает: «сотрудник создан», «запись сохранена», «роль назначена».
Модули подписываются. CRM шлёт приветственное письмо, CMS сбрасывает кеш страницы —
ядро о них не знает.

События типизированы. В отличие от «крючков» WordPress, где связи неявные и отладка
мучительна.

### 4. Дописывание чужих сущностей

Приём из Odoo: модуль добавляет поле в чужую сущность, не переписывая её.
Модуль «Склад» дописывает поле в «Контрагента» из модуля «Продажи» — оба живут независимо.

### 5. Точки вставки в интерфейсе

В оболочке — именованные места, куда модуль вставляет своё: вкладка в карточке,
кнопка в строке таблицы, виджет на главной.

### 6. Изменения базы на уровне модуля

Каждый модуль везёт свои изменения структуры базы. Подключил — таблицы появились,
отключил — остались нетронутыми.

### 7. Совместимость версий

Модуль указывает, с какими версиями ядра работает. Несовместимый не включается
и не ломает систему.

## Разделение клиентов

**Каждая программа — отдельный мир:** свои пользователи, роли, данные.
Менеджер ресторана не видит ничего из центра сертификации и о конструкторе не знает.

Технически: всё в базе привязано к конкретной программе (`Program`). В облаке на одной
установке живёт много программ, в коробке — одна. **Код одинаковый.**

Это решение принято сразу и является самым ценным в фундаменте: обратный переход
от «одна установка — один клиент» к облаку означал бы переписывание всего.

Пока в развёрнутом экземпляре одна программа, определяется в `src/lib/program.ts`.
Когда конструктор начнёт создавать программы, там появится разбор поддомена — остальной
код менять не придётся.

## Технологии

| Слой | Выбор | Почему |
|---|---|---|
| Приложение | Next.js + TypeScript | Один язык на весь стек, быстрая разработка |
| База | PostgreSQL | Надёжность, JSON-поля для гибких сущностей |
| Работа с базой | Prisma | Типизация, управление изменениями структуры |
| Оформление | Tailwind CSS | Единая система стилей, лёгкая тема |
| Запуск | Docker Compose | Одинаково на своей машине и на сервере |

## Порядок построения расширяемости

**Сейчас (дёшево, пока код небольшой):**
реестр вкладов, описание модуля, шина событий, порты для почты и файлов,
права и меню через вклады, изменения базы на уровне модуля.

**Позже (под реальную нужду):**
точки вставки в интерфейсе, дописывание чужих сущностей, изоляция сбойных модулей,
безопасный режим, магазин модулей.

**Риск, о котором помним:** построить роскошную систему расширений раньше, чем появится
что расширять. Поэтому прорезаем швы (потом это дорого), а механику наращиваем по мере
надобности.
