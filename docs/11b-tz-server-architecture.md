# ТЗ: архитектура «основной + страховочный сервер» для скрытого резервирования данных

Дата: 19.09.2026
Статус: черновик, согласован по ключевым решениям, требует практической проверки failover (раздел 5)

## 0. Назначение документа

Документ описывает универсальный паттерн из двух физически разделённых серверов,
который защищает данные приложения от кражи диска/бэкапа и обеспечивает скрытое
резервирование без единой точки отказа. Паттерн не завязан на конкретное приложение —
подходит любой системе, построенной на шине данных (message bus) с воркерами,
не только банкетной CRM «Времена года». Прикладная часть (структура заказов, роли,
функционал банкетов) описывается отдельным ТЗ.

## 1. Ключевое правило (неизменяемое)

Сервер №1 никогда не должен содержать ни в коде, ни в конфигурации, ни в базе данных
ничего, что указывает на существование сервера №2. Любое другое требование, которое
вступает в конфликт с этим правилом, должно быть скорректировано, а не наоборот.

Уточнение по итогам обсуждения: правило распространяется на код, конфиг и БД —
то есть на артефакты, которые остаются в покое. Оно не может распространяться на сам
факт временного сетевого соединения (см. раздел 5) — это физически неизбежно, если
данные передаются в реальном времени. Соединение при этом должно быть неотличимо от
обычного клиента шины, без выделенной учётки, без allowlist по IP на стороне сервера №1.

## 2. Роли серверов

### 2.1. Сервер №1 — основной

Полностью самодостаточен и работает автономно, без сервера №2.

Архитектура:
- Приложение (веб/API) — единственная точка входа для пользователей.
- Шина данных со встроенным кэшем, имеющая публично видимый адрес (это стандартная
  часть архитектуры приложения, не специально добавленный вход для резервной схемы).
- Worker/Agent №1 — потребитель шины, обращается к БД №1.
- БД №1 — хранит только данные, не помеченные как чувствительные.

Приложение всегда обращается к одному и тому же адресу шины и не знает,
кто именно на другом конце обрабатывает запрос.

### 2.2. Сервер №2 — страховочный

Архитектура:
- Worker/Agent №2 — подключается к шине сервера №1 как обычный клиент,
  с теми же учётными данными, что у Agent №1 (отдельная учётка недопустима —
  это стало бы следом на стороне сервера №1), но с более высоким приоритетом
  потребителя.
- БД №2 — полная копия данных, без ограничений.
- Управляющий код — фронтенд/бэкенд для администрирования Agent №2, БД №2
  и связи через мессенджеры (Telegram/MAX).
- Отдельный интерфейс управления защитой (для руководителя) — живёт целиком
  на сервере №2, обращается только к БД №2 и служит для команд управления
  (см. раздел 6 старого ТЗ: `/lock`, `/status`, экстренная блокировка и т.п.),
  а не для просмотра данных. Просмотр полных данных всеми пользователями
  происходит через обычный интерфейс CRM №1, см. раздел 3.

Сервер №2 хранит root-доступ к серверу №1 (пароль/сертификат) — это обычный
административный доступ, не специальный «бэкдор». Используется только для
исключительных случаев (экстренная блокировка, принудительный перезапуск),
а не для повседневной передачи данных — данные идут через шину, не через SSH.

## 3. Нормальный режим работы

- **По умолчанию (штатный режим) Agent №2 подключён.** Все пользователи
  CRM №1, включая менеджеров, видят полные данные, включая помеченные как
  чувствительные — прозрачно, без разделения интерфейса и без индикации
  того, что данные идут через сервер №2. Менеджеры могут не подозревать
  и не должны подозревать, что часть данных, с которой они работают,
  считается чувствительной.
- Agent №2 подключается к шине с более высоким приоритетом потребителя,
  поэтому все новые запросы идёт ему. Он читает и пишет полные данные
  в БД №2 и параллельно дублирует разрешённую (нечувствительную) часть
  в БД №1, чтобы она оставалась актуальной для автономного режима.
- **Автономный режим (Agent №1 + БД №1) — это защитный, деградированный
  режим**, а не режим по умолчанию. Он включается автоматически, когда
  соединение с сервером №2 пропадает (см. раздел 4), либо когда защита
  включена намеренно (директор оборвал соединение). В этом режиме
  чувствительные банкеты незаметно исчезают из CRM — интерфейс продолжает
  работать как обычно, без ошибок и уведомлений пользователю.

## 4. Автоматический возврат в автономный режим

- Если соединение Agent №2 с шиной обрывается (сеть, авария сервера №2,
  осознанное отключение) — шина автоматически возвращает обработку запросов
  Agent №1 и БД №1. Это стандартное поведение приоритетной очереди/failover
  брокера, не специальный код на стороне сервера №1.
- Резервный вариант (если приоритетный failover окажется ненадёжным на
  практике — см. раздел 5): явное включение/отключение Agent №2 через
  разовую root-SSH-сессию сервера №2, без постоянного присутствия кода,
  ссылающегося на сервер №2, на диске сервера №1.

## 5. Что требует практической проверки перед принятием

1. Надёжность и скорость приоритетного failover шины при: обрыве сети,
   аварийном падении сервера №2, штатной остановке. Если не работает
   стабильно — переходим на явное включение/отключение (раздел 4).
2. Поведение кэша шины: ответы с полными данными не должны оседать на диске
   или подолгу висеть в памяти сервера №1 (TTL близкий к нулю или запрет
   кэширования для таких ответов).
3. Учётные данные для шины должны быть общими для обоих агентов и храниться
   в секрет-хранилище, а не в исходниках или системе контроля версий.

## 6. Остаточные риски (не устраняются полностью)

- Пока Agent №2 подключён, само наличие активного соединения с конкретным
  внешним адресом видно в live-инструментах сервера №1 (netstat, список
  процессов брокера) — это неизбежно при любом решении, где данные
  передаются в реальном времени. Смягчается коротким временем жизни сессий
  и отсутствием привязки по IP в конфиге.
- Логи и метрики на уровне провайдера VPS (netflow, биллинг по трафику)
  находятся вне зоны контроля root-доступа внутри сервера №1 и не могут
  быть скрыты средствами самого сервера.
- Публичный адрес шины теоретически доступен любому, кто узнает протокол
  и получит учётные данные — необходима проверка происхождения подключения
  на уровне брокера/файрвола перед сервером №1 (mTLS или сетевой allowlist,
  не хранимый как явный список внутри сервера №1).
- Рекомендация по логированию: минимизировать детальность и срок хранения
  логов по умолчанию, а не чистить их постфактум — чистка после инцидента
  сама является криминалистическим признаком и не защищает от логов
  провайдера, которые лежат вне сервера.

## 7. Закрытые вопросы

- Менеджеры работают с чувствительными данными как с обычными, через
  CRM №1, не подозревая об их статусе (см. раздел 3). Отдельный канал
  сервера №2 предназначен только для управления защитой, не для просмотра.
- **Брокер шины: RabbitMQ.** Единственный из рассмотренных (RabbitMQ, Kafka,
  NATS), где приоритет потребителя (`x-priority`) — штатная документированная
  функция, а не обходной путь. Kafka и NATS балансируют между потребителями,
  а не замещают одного другим, и не подходят под описанную схему.

## 8. План практической проверки failover (перед принятием раздела 5)

На тестовом стенде (два сервера, копия шины, без прод-данных) прогнать:

1. **Штатное отключение** Agent №2 (graceful shutdown) — замерить задержку
   до перехвата запросов Agent №1, проверить отсутствие потери сообщений.
2. **Аварийное падение** Agent №2 (`kill -9`, без закрытия соединения) —
   замерить время до срабатывания heartbeat-таймаута RabbitMQ и переключения.
3. **Разрыв сети** между серверами (блокировка firewall-правилом, не падение
   процесса) — тот же замер простоя.
4. **Возврат Agent №2** после восстановления связи — проверить, что ни один
   запрос не обработан дважды и ни один не потерян при перехвате приоритета.

Критерий принятия: простой в сценариях 2–3 не превышает согласованный порог
(предварительно предлагается 5–10 секунд — требует подтверждения заказчиком
исходя из требований к доступности CRM), без потерь и дублирования в
сценарии 4. Если критерий не выполняется — переходим на резервный вариант
явного включения/отключения через root-SSH-сессию (раздел 4).
